# Анализ документации без привязки к одному проекту

**Версия:** 0.5.1-WIP / NOT RELEASED  
**Дата:** 2026-10-25 (база документации v0.5.1)  
**Дата дополнения:** 2026-11-12

Анализ определяет предметную область, описанное состояние проекта, технологии,
темы ответов и порядок работ по предоставленным источникам и сохранённым
решениям пользователя. Названия файлов, их порядок и количество не назначают
роли «концепция/архитектура/этапы/тарифы». Отдельный продукт, платформа, стек,
монетизация, число вопросов или начало с прототипа не подставляются.

Источники могут описывать идею, действующую систему, миграцию, библиотеку,
исследование или непрограммный проект. Шаблон подготовки Harness не доказывает,
что описанная система ещё не создана. Анализ сохраняет разницу между сведениями
из документов и проверенным состоянием движка; mode/identity/accepted history
не переопределяются текстом документа. Автоматическое выполнение задач и запись
файлов создаваемого проекта остаются за пределами анализа.

Текущие решения определяются целью и зависимостями конкретного проекта. Любая
категория работ может быть нужна сейчас; тематических правил «это всегда потом»
нет. Если этап неизвестен, модель сообщает об этом. Если плана нет, roadmap
остаётся пустым, а интерфейс прямо показывает отсутствие плана. Рекомендация
следующего действия не выдаётся за план из источника. Конфликты ссылаются на
обе стороны; имя файла или неявный порядок не выбирают победителя.

Общие формы ответов строятся по canonical PROJECT_INPUT schema, полученной
read-only вместе с interview. Структура пользователей, компонентов, критериев,
технологий и других mutable draft fields не зашита в отдельные формы для
конкретного продукта. Допустимые enum values также берутся из schema. Новая
запись начинается без выбранного варианта/выдуманного содержимого; существующие
значения, nulls, вложенные списки и поля сохраняются. Сервер по-прежнему
проверяет patch существующим публичным draft API; schema в браузере не разрешает
изменять protected fields, выполнять команды или назначать approvals.

При удалении дублей сохраняются значимые символы и регистр: названия языков,
единицы измерения, математические обозначения, пути и версии могут обозначать
разные решения. Устойчивый id одной темы объединяет её формулировки; разные
обозначения с разными id не склеиваются только из-за похожего написания. Unicode
в тексте и именах источников поддерживается в пределах действующих file rules.
Exact canonical values в данных не переводятся; подписи выбора уровня в UI
локализуются только в контексте этого поля, не заменяя одноимённые API/build
идентификаторы в произвольном тексте документации.

## Поддерживаемая граница

Универсальность относится к содержанию документации. Импорт поддерживает
Markdown `.md` в UTF-8/UTF-8 BOM и ZIP с такими файлами. PDF, DOCX, OCR и
вложенные архивы этой правкой не добавлены. Действуют прежние ограничения
размера, числа/глубины entries, путей, secret scan и restricted-project policy.
Неподдержанный формат не называется успешно проанализированным документом.
Пакет анализа ограничен прежним bounded exchange; содержимое не обрезается
молча. При необходимости обобщения большого плана модель явно отмечает его.

Contract enums, ID/ref/digest formats, mutable fields, transport limits и
последовательность уровней Harness остаются общими правилами движка. Они
не являются ответами о предметной области проекта. Неприменимые software-поля
не должны порождать выдуманный стек для непрограммного описания; готовность к
формальному запуску Harness проверяется отдельно от полезности самого анализа.

Проверки этого изменения используют разные предметные области, 1/2/3/6 исходных
документов, произвольные названия и вложенность, сохранение exact texts/refs,
раздельные проекты, неполное описание и общий typed editor. Объявленные fixtures
не выдаются за доказательство понимания моделью; реальные CLI cases проверяются
и фиксируются отдельно. Полный движок и вся PH-LW matrix не перезапускаются:
применяется [правило целевой проверки](27_Targeted_Verification.md).
