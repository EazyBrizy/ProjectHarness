# Проверка исходного AGENTS.md

Исходник сохранён как [AGENTS.original.md](AGENTS.original.md) и в `_inputs/AGENTS.md`. Основные архитектурные и safety-инварианты полезны; проблема — объём, повторения и устаревшее состояние задачи. Новый AGENTS: 36 строк вместо 153, примерно 4,7 тыс. символов вместо 16,3 тыс.; детали вынесены в связанные рабочие документы.

| Наблюдение | Изменение |
|---|---|
| §3 объявляет PH-LW-04 текущей базой, а PH-LW-05 будущей | Точная PH-LW-05 пара и hashes закреплены в CURRENT_TASK; оба этапа принимаются в рамках пользовательского задания |
| Большой регламент смешивает постоянные ограничения, текущий статус, команды и формат выдачи | AGENTS сокращён; карта источников, состояние и runbook вынесены в отдельные связанные файлы |
| Таблица ссылок не включает главу PH-LW-05 importer | Добавлена связь prompt → docs → модули → tests/CI |
| Требуется внешний SHA256, которого среди входов нет | Отдельно различаются manifest integrity, наблюдаемый ZIP hash и отсутствующая внешняя attestation |
| Предписан Python 3.14, но среда не проверена; примеры предполагают py launcher | Отдельная локальная среда, точный interpreter и deps в evidence; CI должен поддерживать прямой python.exe |
| Примеры исторических docs предлагают ExecutionPolicy Bypass | Рабочий runbook не требует ослабления политики; исходные исторические документы сохранены |
| Комплект docs содержит исторические PLANNED/NOT RUN рядом с поздними implementation reports | Свежий статус в CURRENT_TASK и новом acceptance report; старые статусы не превращаются задним числом в PASS |
| Нет автоматической проверки карты workspace и зеркал | Добавляются воспроизводимый archive preflight и проверка связности/побайтовых mirrors |

Что важно не упустить при приёмке: настоящий Waitress/Edge вместо только Flask client; multipart upload через TCP и браузер; Windows reparse/hardlink и rollback; повтор POST с прежним key/revision; запуск установленного wheel вне source; PowerShell stderr/exit/skip accounting; точные финальные ZIP hashes и отдельные verdicts. Наличие Windows CI скрипта не доказывает, что его команды когда-либо успешно выполнялись.

Нормативные запреты на Git/provider/parallel execution относятся к функциям **движка**. Их нельзя автоматически трактовать как запрет разработчику использовать обычные локальные инструменты тестирования. Скачивание зависимостей для среды разработчика также не означает, что приложение получило сетевой доступ к пользовательским документам.

После фактической проверки дополнительно выявлены: неверная подпись лимита ZIP в UI, Windows fsync дефект Stage transaction, stale check перед HTTP replay, неоднозначные multipart поля, parent-junction и raw-ZIP budget проблемы, зависшие busy buttons и неработоспособный старый PowerShell CI. Исправления и evidence — в [новом отчёте](../Project_Harness_Engine_v0.5.1/PH_LW_04_05_WINDOWS_ACCEPTANCE_TEST_REPORT.md).

Открытые вопросы, которые нельзя спрятать правилами AGENTS: старая миграция v0.5.0→v0.5.1 содержит отдельный Windows fsync defect; Unix/Podman suites не стали Windows-compatible; file-symlink и case-sensitive alias coverage ограничена правами/настройкой этой машины; clean-machine installer ещё не проверен. Всё это отражено отдельными FAIL/SKIP/NOT RUN, а не закрыто общим PASS. Source и fixtures для автоматического режима/миграции не переписывались в текущем HTTP scope.

В предоставленном каталоге не было Git metadata. Репозиторий, remote и commits не создавались: для этого переноса точная база и diff восстановимы из `_inputs`, manifests и [машинного списка изменений](ENGINE_CHANGES.json). Перед следующей крупной итерацией полезно выбрать постоянный репозиторий/backup policy; это рекомендация, не дополнительный обязательный gate текущего задания.
